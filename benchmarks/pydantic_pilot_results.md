## B. Internal round-trip reconstruction (SpecificPitch)

| Path             | Mean ± stdev (ms) |
|------------------|-------------------|
| `model_construct` (internal round-trip regime) | 454.9 ± 50.2 |
| `model_validate` (trust-boundary regime)       | 298.6 ± 30.4 |
| Speedup                                        | **0.66×** (model_construct < model_validate) |

**Surprise:** `model_construct` is SLOWER than `model_validate` on this scalar.  Pydantic v2's `model_validate` calls into an optimised Rust validator; `model_construct` runs pure Python and on a frozen model pays per-field `__setattr__` overhead. The implication: internal-round-trip reads should NOT routinely call `model_construct` per row when `model_validate` is available — the design assumption (construct is faster) does not hold for this pydantic / scalar shape.  Per WP2's locked regime contract, `model_construct` remains the correct semantic choice for trusted internal data (it bypasses validation), but its performance benefit on this scalar shape is negative.  This is flagged for the bulk-migration commission to reconsider before standardising the regime call sites.

## Conclusion

**WP2 GATE A PASSES — bulk pydantic migration justified.** Column-builder is ≥ 2× faster than row-wise `model_dump` for the Coordinate scalar, so the column-builder pattern is the canonical bulk path for the 15+ scalars in the bulk migration.

## WP2 bulk addendum (2026-05-21)

After the bulk migration landed (15 scalars now pydantic v2 ``BaseModel``):

### DcmlHarmony (100k instances, 5 runs)

| Path                              | Mean ± stdev (ms) |
|-----------------------------------|-------------------|
| column-builder                    | 136.7 ± 7.1 |
| `model_dump` row-wise (forbidden) | 267.5 ± 4.7 |
| Speedup                           | **1.96×** |

Column-builder is ~2× faster than `model_dump` row-wise on the 11-field
DcmlHarmony scalar — gate held under bulk migration.  Speedup is smaller
than Coordinate's 4.4× because the per-row cost of pulling 11 string +
optional-int attributes via `getattr` is closer to the cost of
`model_dump`'s dict creation; both paths spend most of their time in
``pa.array`` ingest.  Conclusion: the gate threshold of 2× is met; the
column-builder remains canonical.

### Note with nested Coordinate / Duration (50k instances, 5 runs)

| Path                              | Mean ± stdev (ms) |
|-----------------------------------|-------------------|
| column-builder (recursive)        | 112.1 ± 3.6 |
| `model_dump` row-wise             | n/a (shape mismatch) |

`model_dump` is omitted because `Note.pitch` is dropped from the
pa.Schema via the value projector — the row dict from `model_dump`
carries `pitch`, which `pa.array` rejects against the derived struct
type.  This is itself a piece of evidence that the column-builder /
projector pair is the correct architecture: row-wise paths can't
honour columnar separation without re-implementing the projector logic.
The recursive column-builder (added in WP2 bulk) descends into
`Coordinate` and `Duration` slots via `build_coordinate_struct_array`,
preserving the denormalised `{value, numerator, denominator}` storage
struct end-to-end.
