## Alignment Relationships

All files represent the same musical content with "perfect alignment" (bijective linear mapping):

```
DGT1 (Piano Roll Image: 299400 px)
  |
  +-- DGT1_child (Punch Holes Region: 15343 - 293119 px = 277776 px)
  |       |
  |       | 1:1 mapping: pixel_row -> tick (relative to first hole)
  |       v
  +---- DLT1 (MIDI-raw: 30092 notes, 277776 ticks total)
           |
           | Merged adjacent holes
           v
        DLT2 (MIDI-expressive: 6380 notes, 273249 ticks)
           |
           | Tempo map -> seconds
           v
        DPT1 (MP3: D seconds, minus 2s resonance at end)
           |
           | Perfect alignment (same performance)
           v
        CLT1 (Score: 888 quarterbeats, 5577 notes)
```

### Alignment Anchors

For the single-group scenario, these start/end pairs form the perfect alignment:

| Timeline | Start | End | Unit |
|----------|-------|-----|------|
| DGT1 (image) | 0 | 299400 | pixels |
| DGT1_child (holes) | 15343 | 293119 | pixels (in parent coords) |
| DGT1_child (relative) | 0 | 277776 | pixels (relative to first hole) |
| DLT1 (raw) | 0 | MIDI_TOTAL_TICKS | ticks |
| DLT2 (exp) | 0 | MIDI_TOTAL_TICKS | ticks |

## Validation Logic

### Why We Know the Alignment is Correct

1. **DGT1_child <-> DLT1**: The raw MIDI file was generated by SUPRA's analysis pipeline that maps each hole punch (in pixel coordinates) to a MIDI tick. The relationship is deterministic and 1:1 within the musical region.

2. **DLT1 <-> DLT2**: The expressive MIDI is derived from the raw MIDI by merging adjacent holes representing the same note. Total note count is preserved; only note-on/off times and durations change.

3. **DLT2 <-> DPT1**: The MP3 is a direct synthesis of the expressive MIDI. Same tempo map applies, with 2 seconds of resonance added at the end.

4. **DLT1/DLT2 <-> CLT1**: The score encoding represents the same piece. While the exact note counts differ (score includes all voices, MIDI includes only what was punched), the temporal structure (measures, quarterbeats) maps linearly to the MIDI tick timeline.

### Known Discrepancies

2. **Score vs MIDI note counts**: The score has 5577 notes; the MIDI has 8718 "musical notes" (merged holes). This is expected because:
   - The piano roll may include octave doublings
   - Expression tracks may add control holes counted as notes
   - The piano arrangement differs from the original orchestral score

3. **MP3 resonance**: The MP3 file includes ~2 seconds of silence/decay at the end that is not part of the musical content.

## Test Requirements

### ZERO TOLERANCE Policy

All test assertions MUST use exact expected values:

```python
# CORRECT
assert loader.rollinfo["MUSICAL_HOLES"] == 30092

# WRONG - No ranges or minimums
assert loader.rollinfo["MUSICAL_HOLES"] >= 30000
```

### Required Test Cases

1. **IIIFManifestLoader**
   - Extracts width=4096, height=299400 from manifest
   - Handles missing/malformed manifests gracefully

2. **ATONLoader**
   - Parses ROLLINFO metadata with exact values
   - Parses all HOLE blocks (verify count matches or document discrepancy)
   - Extracts FIRST_HOLE, LAST_HOLE correctly
   - Each hole has required fields (ORIGIN_ROW, TRACKER_HOLE, etc.)

3. **AlignmentBundle**
   - Order independence: same result regardless of timeline add order
   - Transfer coordinates correctly between all timeline pairs
   - Summary output is deterministic

4. **MIDI Loaders**
   - Raw MIDI: exactly 30,092 notes (matches MUSICAL_HOLES from ATON)
   - Expressive MIDI: exactly 6,380 notes (merged adjacent holes)
   - Tick ranges align with ATON pixel ranges

5. **Score Loader (TSV)**
   - Exactly 5577 notes
   - Exactly 222 measures
   - Total length: 888 quarterbeats
